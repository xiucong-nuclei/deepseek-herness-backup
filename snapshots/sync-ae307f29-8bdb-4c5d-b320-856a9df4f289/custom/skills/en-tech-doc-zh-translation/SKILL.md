# 英文技术文档中译流程（EN → ZH）

## 0. 适用范围

- 用于：英文技术书、长文档、markdown 文档仓库的**整篇中译**。
- 不用于：中译英（用 `spec-trans`）；单句/短摘要翻译（直接译即可）。
- 目标风格：**易懂、准确、精炼、专业**。四者优先级：准确 > 易懂 > 精炼 > 专业（准确不可为通顺让步）。

## 1. 交付物布局（先定死，再动笔）

1. 在原文仓库的本地 clone 中新建 `zh/`，**文件名与原文一一对应**（`chapter-01.md` → `zh/chapter-01.md`）。
2. **原文一律不改、不删**。译文与原文并存，便于对照 review。
3. 图片仍留在仓库根目录，译文引用必须改为相对上级目录：`![…](../fig3-4-lmul-register-grouping.png)`。这是最容易漏的一步。
4. `zh/GLOSSARY.md`：术语对照表，**先于正文产出并单独提交**。
5. `zh/README.md`、`zh/index.md` 同步翻译；书目引用（citation / BibTeX / 人名 / 出版社）保持英文原样，仅在其旁加一行中文说明。
6. `LICENSE` 不翻译、不修改。

## 2. 流程

| 阶段 | 动作 | 产出 |
|---|---|---|
| P0 勘察 | clone；统计规模、章节结构、图表引用方式、文体（第一人称叙事 vs 参考手册 vs 混合） | 章节清单 + 文体判断 |
| P1 术语先行 | 抽出高频术语，定唯一译法 | `zh/GLOSSARY.md` + 提交 |
| P2 逐章翻译 | 一章一文件、**一章一提交**；长章可内部拆分推进，但提交粒度按章 | `zh/chapter-0N.md` ×N |
| P3 一致性回扫 | 跨章术语、称谓、图表编号统一；错译修正单独提交 | 回扫修正提交 |
| P4 交付说明 | 章节清单、提交列表、遗留问题 | 聊天中的要点汇报 |

- 规模判断：≤ 600 行可单 agent 顺序译；上千行或 6 章以上，按章并行（见 §9）。
- **P1 必须先冻结 glossary 再开并行**，否则各章术语必然漂移。

## 3. 语言风格细则

**易懂**
- 拆长句：英文的从句套从句，改成中文短句串接，必要时重排语序。
- 保留作者第一人称叙事：原文说 "I built…" 就译"我构建了…"，**不要**改成"笔者/我们"，也不要改成无人称手册腔。
- 抽象的比喻保留（"the secret sauce" → "秘诀所在"），不删。

**准确**
- 术语按 glossary 固定译法，一次选定、全程不改。
- 位宽、编码位域、数字、CSR 名、指令名、条件（`vl > 0`）一律照抄，不换算、不改写。
- 不意译技术名词；拿不准就保留英文原词并加中文说明，不要硬造词。

**精炼**
- 删英文冗余连接与客套："It is important to note that…" 直接陈述；"In this section, we will…" 可省则省。
- 不加原文没有的解释、例子、总结；不写"综上所述""总而言之"式填充。
- 不重复首现术语的英文（glossary 已记录）。

**专业**
- 用工程界通行说法：乱序执行、寄存器重命名、条带挖掘、归约、掩码、寄存器堆。
- 不用口语（"搞""弄""搞定"），不营销化（"业界领先""革命性"），不加感叹号。
- 语气平实客观；原文若有作者主观意见，用"我认为/在我看来"如实保留，不改写成定论。

## 4. 格式保真（硬规则）

- 标题层级与编号原样保留（`## 1.15.3 …`），只译标题文字。
- Markdown 结构不变：表格、列表、加粗、引用块、围栏代码块、`---` 分隔线。
- **不译**：代码块内容、指令名（`vsetvli`）、CSR（`vtype`/`vl`）、寄存器名（`v0`）、文件名、公式、URL、Hex/二进制常量。
- 图片：`alt` 文本与图注（`**Fig. 4-9.**`）译文字、编号保留；路径按 §1.3 改 `../`。
- 表格：只译表头与单元格文字；分隔行不必按显示宽度重算（markdown 渲染自适应）。
- 标点：正文用中文全角标点；中英文/数字与汉字之间加一个半角空格；`—` → `——`；引号 `" "` → `""`。
- 不做 markdown 之外的改造：不新增目录、不加 emoji、不重排章节、不合并小节。

## 5. 术语治理

- 缩写（RVV/SEW/LMUL/VLEN/VLMAX/GEMM/PE/CSR/VRF）**保留英文**；首次出现写 `中文（English）`，之后只用缩写或中文。
- 高频硬件词（lane、chaining、tile）首次出现给中文（通道／链接／瓦片）+ 英文，之后统一用中文。
- 同一术语全库唯一译法：发现分歧 → 改 glossary → **回扫已译章节**。
- 术语表格式：`| English | 中文 | 首现/说明 |`。
- 参考：RISC-V 向量类文档可直接复用 `references/glossary-riscv-vector.md`。

## 6. 提交协议（git）

- 一个逻辑单元一次提交：术语表 1 次、**每章 1 次**、回扫修正 1 次。
- 提交信息用中文、conventional 前缀：
  - `docs(zh): 新增术语对照表`
  - `docs(zh): 翻译第 3 章 RISC-V 向量扩展基础`
  - `docs(zh): 统一第 1-6 章术语与图表编号`
- 提交信息中写清范围（新增 `zh/chapter-03.md`），明确"翻译"不是"修改原文"。
- 不 push，除非用户明确要求（原书常为 CC BY-NC-ND 类许可，见 §8）。
- 若 clone 出来的仓库没有 git 身份，先 `git config user.name/user.email`（本地配置即可）。

## 7. 每章质检清单

配套检查脚本：翻译仓库内 `zh/tools/check_zh.py`（校验标题编号序列、代码块逐字、图片路径可解析、表格/列表/引用块计数、残留英文整句、半角标点；`python3 zh/tools/check_zh.py` 或带章号）。README / index 等非章节文件不在脚本覆盖内，需人工核。

- [ ] 结构、编号与原文一一对应，无漏段漏表
- [ ] 图片路径为 `../fig*.png` 且文件真实存在
- [ ] 代码块逐字未改（可 `diff` 抽取对比）
- [ ] 术语与 glossary 一致，无同词多译
- [ ] 无残留英文整句（引用、术语首现、代码除外）
- [ ] 正文无半角逗号/句号混入，中英文间空格统一
- [ ] 无机器翻译腔（"这是重要的注意""被进行"）、无臆造内容
- [ ] 第一人称叙事章节语气未被改成手册体

## 8. 常见坑

- **图片路径**：译文放子目录后原相对路径失效，必须改 `../`。
- **文体混合**：同一本书里叙事章与手册章语气不同，随原文，不要全书统一。
- **专名不译**：人名、公司、产品名、芯片代号（Cray-1、AndesCore NX27V）保持原样。
- **许可**：CC BY-NC-ND 一类许可下翻译属演绎作品，交付时提示用户许可限制，不要代为发布或推送到公开远端。
- **并行漂移**：先冻结 glossary；并行章节 prompt 里必须带 glossary 路径。
- **别顺手"改进"原文**：原文的口语化解释、作者个人经历都要如实译出，不做删减或"优化"。

## 9. 长文档并行翻译

- 每章一个 subagent，prompt 必须自包含：skill 路径、glossary 路径、原文路径、输出路径、图片路径规则、该章文体提示、返回格式（只回简短报告，不贴译文）。
- 主 agent 负责：写 glossary → 串行提交 → 回扫一致性；subagent 不执行 git 命令（避免并发写 index）。
- 每批 3–6 章并行；单章超 1500 行时按小节拆两批并在 glossary 之后单独指定衔接点。

## 10. 导出 PDF（可选交付）

- 工具链：**python-markdown（md→HTML）+ weasyprint（HTML→PDF）**，纯 Python、无需 LaTeX 与 root。依赖装到工作区内的 `--target` 目录（本机为 `/home/ubuntu/riscv_docs/pylibs`，已 gitignore）：`python3 -m pip install --target=<dir> weasyprint markdown`，运行加 `PYTHONPATH=<dir>`。沙箱内 `sudo` 不可用、Python 又缺 `ensurepip`（`python3 -m venv` 会失败），所以不要走 venv/apt 路线。
- 结构：`书名页 + md.toc 目录 + 正文拼接 + 术语表附录`，全部输出到一个 HTML 后一次渲染。
- CSS 要点：`@page` 页脚 `counter(page)`、`h1 { break-before: page; string-set: chaptitle content() }` 配 `@top-right { content: string(chaptitle) }` 做页眉、`img { max-width: 100% }` 防宽图溢出、`table/pre { break-inside: avoid }`。
- 两个坑：① python-markdown 生成的目录是 `<div class="toc">`，CSS 选 `nav.toc` 会静默失效（表现为目录无页码、链接回落到默认蓝色）；② 译文里的 emoji（📘➡️⭐）在 CJK 字体中无字形会显示成方框，构建时用正则剔除，`→` 等符号保留交给字体回退。
- 目录页码用 `content: target-counter(attr(href), page)`，前提是正文标题 id 与目录 href 完全对应，构建前应校验一遍（无重复 id、无解析失败的 href）。
- 参考实现：`riscv-vector-primer/zh/tools/build_pdf.py` 与同目录 `README.md`。

## 11. 成稿润色（通顺性打磨）

触发：译文读起来有翻译腔/不通顺，或用户明确要求润色。**润色不是重译**——不改内容，只改表达。

**第一原则：通顺。** 验收标准是"中文母语的工程师读一遍就懂，不需要回读"。

**硬性必查项**

1. **禁止第二人称**：技术文档不出现"你、您、你们的"。改法按语境选择——无主语句、具体主语（读者/设计者/开发者/软件/处理器/编译器）、或直接陈述事实。不要机械替换成"读者"（满篇"读者"同样不自然），也不要一律改成"我们"回避（除非原意确为作者与读者共同视角）。作者自述的第一人称"我"必须保留。
2. **长定语拆句**：英文式的"一个……的、……的、……的 X"拆成几个短句或改为后置分述。
3. **去翻译腔**：删"被进行/被用于"式被动堆叠（改主动或无主句）；"然而/此外/因此"等连接副词只在真需要转折递进时保留；英文式抽象名词主语（"……的一个好处是"）能换成人或物做主语的换掉。
4. **术语不动**：译法按 glossary，润色不得引入新译法，也不得改动已有术语。
5. **结构与格式一字不动**：标题及编号、代码块、行内代码、图片路径与图注编号、表格行列、列表、分隔线、缩略语与专有名词。
6. **一段一行**不变：不拆段落、不合并段落。
7. **内容零改动**：事实、数字、结论、语气强弱（允许/必须/可能/由实现定义这类情态词）、比喻、作者个人经历与口语化表达一律保留。

**流程与规模**：逐章并行（每章一个 subagent，prompt 内含上述必查项 + "只改确实不通顺处，好句子留着"）；README/术语表单独一个。润色后必须①重跑 `check_zh.py` 确认结构未破，②重新生成 PDF，③按章提交（提交信息写明"润色：通顺性打磨 + 清除第二人称"）。
