# SDLC 审查技能

独立核验从 Kanban 实现运行交接（handoff）到审查通道的工作，然后批准、要求修改或升级。本技能审查交付物及其证据；它不接管实现者的工作。

## 何时使用

满足以下所有条件时使用本技能:

- 调度器（dispatcher）因为你领取了 `review` 通道的任务而派生你；
- 实现者提交了 `review_requested` 交接；
- 任务在完成之前需要独立的裁决。

不要将它用于单独的下游审查卡片。下游卡片只是带有审查导向规格的普通实现工作，走它自己的生命周期完成。

## 前置条件

- 一个带有当前任务和运行标识符的 Kanban worker 上下文。
- 原生 Kanban 工具: `kanban_show`、`kanban_comment`、`kanban_complete`、`kanban_request_changes` 和 `kanban_block`。
- 当交付物是代码时，可通过 `read_file`、`search_files` 和 `terminal` 访问工作区。
- 任务的原始规格、验收标准、交接摘要和既往运行历史必须能通过 `kanban_show` 获取。

## 如何运行

本技能由审查调度器自动加载。在检查文件或选择裁决之前，先从 `kanban_show` 开始。

1. 阅读任务规格和最新的 `review_requested` 交接。
2. 检查实际交付物并运行相关验证。
3. 只选择一个裁决: 批准、要求修改或升级。
4. 在最终的 Kanban 状态转换中记录具体证据。

## 快速参考

| 裁决 | 何时使用 | 最终操作 |
|---|---|---|
| 批准 | 验收标准和验证均通过 | `kanban_complete` |
| 要求修改 | 仍存在可修正的实现缺陷 | `kanban_comment`，然后 `kanban_request_changes` |
| 升级 | 需要人类决策或外部前置条件 | `kanban_block` |

要求修改的状态转换会把任务退回给原实现者。当该实现者再次请求审查而未指定审查者时，持久化的审查者来源信息会将重新审查路由回同一个审查者档案。

## 审查视角

每轮都要变换看待工作的方式，而不是重复同样的检查。去相关的视角能捕获不同的缺陷类别: 冷读工件会暴露实现者叙事中不会提及的设计和正确性问题；执行会暴露无法复现的说法；严格的契约审计会暴露悄然发生的作用域漂移。在第 3 轮重复第 1 轮的视角，大多只会重新发现第 1 轮已发现的问题。

根据任务记录已有的历史确定当前轮次: 统计 worker 上下文中"本任务的既往尝试"部分（在 `kanban_show` 中也显示为先前的运行）里 `changes_requested` 条目的数量。当前审查轮次等于该数量加一。因此第 1 轮显示零次 `changes_requested` 尝试；第 2 轮显示一次；以此类推。

| 轮次 | 视角 | 如何应用 |
|---|---|---|
| 1 | 工件（Artifact） | 在阅读实现者摘要之前，先冷读 diff 或交付物。形成独立判断，再与交接叙事对照，逐一调查所有不一致之处。 |
| 2 | 执行（Execution） | 检出工作并通过 `terminal` 实际运行它: 亲自构建、测试并演练所报告的行为。逐条实证核验交接中的每个说法，而不是重读工件。 |
| 3+ | 契约（Contract） | 重新阅读**原始**任务正文和验收标准，然后严格对照它们审计交付物。同时核验此前每一轮 `kanban_request_changes` 的每个条目是否真正落地。 |

"程序"一节的基线职责在每一轮仍然适用；视角决定你以哪种检查为主并赋予最大权重。

### 临时审查分派中的视角变化

同样的原则也适用于 Kanban 审查通道之外。通过 `delegate_task` 派生多个并行审查者时，给每个审查者不同的视角——一份只看 diff 的任务书、一份全上下文任务书、一份检出并运行的任务书——而不是相同的任务书。相同的任务书会产生关联的裁决和重复的发现；变化的任务书在同样的审查投入下能覆盖更多缺陷类别。

## 程序

### 1. 从持久任务记录中定位

调用 `kanban_show` 并识别:

- 原始任务正文和验收标准；
- 最新的实现摘要和结构化元数据；
- 变更的文件、提交标识符和测试证据；
- 早期运行留下的评论和决策；
- 先前审查轮次的发现。

把交接视为需要核验的说法，而不是工作正确的证明。

### 2. 对比所要求的行为与交付的行为

把每条验收标准映射到具体的实现或输出证据。在决定是否进行更深入检查之前，记录遗漏、语义变化和不相关的范围。

对代码类工作:

1. 使用 `read_file` 和 `search_files` 检查变更的路径及其调用方。
2. 使用 `terminal` 检查 diff 并运行项目现有的针对性测试、lint、类型检查或构建命令。
3. 在可行时演练所报告的失败路径以及至少一条普通控制路径。
4. 检查与变更相关的错误处理、边界情况、并发边界、数据保留、安全边界和跨平台行为。
5. 确认测试断言的是行为，而不是仅仅对源代码文本或常量做快照。

对非代码类工作:

1. 检查完整的交付物，而不仅仅是其摘要。
2. 检查正确性、完整性、格式和来源信息。
3. 当引用的 URL 或外部事实影响裁决时，用适当的原生工具验证它们。

### 3. 选择一个裁决

#### 批准

仅在验收标准得到满足且证据充分时批准。调用:

```text
kanban_complete(
    summary="Reviewed and approved. <what was verified>",
    metadata={"review_outcome": "approved", "reviewer_checks": [...]}
)
```

包含实际通过的检查项，以及任何不阻碍验收的有界保留意见。

#### 要求修改

用于具体的、可修正的缺陷。首先记录可操作的发现:

```text
kanban_comment(
    task_id="<current-task-id>",
    body="Changes requested:\n1. <file or artifact + defect>\n2. <required correction>",
)
```

然后把同一任务退回给实现者:

```text
kanban_request_changes(
    reason="<concise summary of the required corrections>"
)
```

说明缺陷在哪里、如何复现、为何违反任务要求，以及什么最低限度结果可以解决它。该状态转换不使用阻塞者重复计数。

#### 升级

仅在审查者和实现者无法在没有人类决策或外部前置条件的情况下解决问题时使用升级:

```text
kanban_block(
    reason="escalation: <decision or prerequisite required>"
)
```

说明被阻塞的决策以及继续推进所需的最小信息。

### 4. 保持角色分离

以审查者身份行事时不要编辑实现。要求修改并让实现者产出下一个候选版本；然后在下一轮审查中独立核验该候选版本。

## 常见陷阱

- **橡皮图章式批准:** 一份通过的交接摘要不是独立证据。
- **审查者动手实现:** 编辑交付物会掩盖所有权归属并削弱重新审查的边界。
- **模糊的发现:** “需要改进”不能给实现者一个可复现的修正目标。
- **仅因风格而阻塞:** 当行为和仓库标准都已满足时，不要仅为偏好级别的细枝末节要求修改。
- **跳过先前轮次:** 重新审查必须同时确认所要求的修正和先前通过行为的保持。
- **用阻塞处理普通返工:** 可修正的缺陷属于 `kanban_request_changes`；`kanban_block` 保留给真正的外部阻塞或人类决策。
- **无证据即完成:** 每条批准摘要都必须点名实际检查过的检查项或工件。

## 验证

提交裁决前，确认:

- [ ] 已为当前任务和运行读取 `kanban_show`。
- [ ] 每条验收标准都已映射到证据。
- [ ] 实际交付物已检查。
- [ ] 相关针对性检查已运行，或无法执行时记录了明确原因。
- [ ] 先前要求修改的条目在重新审查时已重新测试。
- [ ] 已考虑不相关的回归和作用域变化。
- [ ] 裁决只使用一个最终操作。
- [ ] 摘要包含具体、非机密的证据。
- [ ] 审查者未编辑任何实现文件。
