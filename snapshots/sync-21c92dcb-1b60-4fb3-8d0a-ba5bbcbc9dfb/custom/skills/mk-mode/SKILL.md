# !mk 模式 — 单一代码块 Markdown 输出

## 使用时机

用户消息以 `!mk` 前缀开头。

为什么用 `!` 而不是 `/`：Hermes 网关（WeCom 等）会把 `/` 拦截为内置斜杠命令前缀。任何以 `/` 开头的自定义触发词都会导致 "unknown command"。改用 `!`。

触发后，整个响应必须包裹在单个代码块中，以便用户复制到 Typora（或任意 Markdown 编辑器）时，不会因聊天平台的富文本渲染而损坏格式。

## 工作流程

### 第 1 步：检测触发词

检查用户消息是否以 `!mk` 开头：

- `!mk <内容>` — 用户希望响应放在代码块中
- 去掉 `!mk` 前缀，把其余部分当作实际消息
- 不要试图把 `!mk` 注册为斜杠命令 —— 它纯粹是 agent 层面的提示

### 第 2 步：格式化响应

先用完整的 Markdown 格式正常生成响应，然后把全部内容包裹进**单个**代码块：

````
```md
[Your full Markdown response here — one continuous block]
```
````

### 第 3 步：代码块规则

- 开围栏：````md`（或裸 ````）
- 闭围栏：````
- **整个响应放在一个块内** —— 不要拆成多个代码块
- 所有 Markdown 元素都放进去：标题、表格、列表、代码、粗体/斜体、链接
- 内部代码片段：用**4 空格缩进**代替三个反引号，避免与外层围栏产生嵌套问题
- 开/闭围栏前后不要紧挨着空行

### 第 4 步：块内内容格式

- 全程使用标准 Markdown（标题用 `##`，表格用 `|`，列表用 `-`）
- 行内代码用单个反引号 `` ` ``（在外层围栏内是安全的）
- 代码块用 4 空格缩进，不用三个反引号
- 让内容自包含 —— 用户会把整个块粘贴进 Typora

## 平台说明

- **WeCom (企业微信)** 会把外层围栏渲染为单个可滚动文本框。内部 Markdown 内容不会被渲染 —— 保持纯文本。用户复制整个文本框粘贴进 Typora 后再由其渲染。
- **其他平台**（CLI、Telegram）对内层 Markdown 的渲染方式可能不同。在这些平台上，要考虑是否真的需要 `!mk` 模式。

## 示例

### 示例 1：代码分析

用户：`!mk 分析这段代码的逻辑`

响应：

````
```md
## 函数分析

| 函数 | 作用 |
| :--- | :--- |
| foo() | 初始化硬件 |
| bar() | 执行核心逻辑 |

### 执行流程

1. foo() 配置寄存器
2. bar() 开始轮询
```
````

### 示例 2：含嵌套代码的 Bug

如果响应中包含代码块，内部改用 4 空格缩进而不是反引号：

````
```md
## 配置方法

运行以下命令启动服务：

    systemctl start myservice
    systemctl enable myservice

| 参数 | 说明 |
| :--- | :--- |
| --port | 监听端口 |
```
````

## 常见陷阱

- **嵌套反引号** —— 绝不要在 ```` 围栏内放三个反引号。代码块用 4 空格缩进。
- **不要拆开** —— 一个响应 = 一个代码块。绝不能拆成多个块。
- **不要用 `/mk`** —— 斜杠前缀会在 Hermes 网关上报 "unknown command"。始终用 `!mk`。
- **长内容** —— 很长的 Markdown 复制可能较慢，但对这个用例可以接受。
- **图像提取准确率** —— 视觉模型偶尔会漏行（尤其是在边缘附近，或首行与之前的图片不同时）。从截图提取文本时：(1) 数一下行数，对照用户预期核对完整性；(2) 用户说少了某行就立即重新提取 —— 用户能看到图片而模型不能；(3) 如果用户拿之前显示 N 行的图片对比，而本次提取只有 N-1 行，那很可能是截图截掉了一行，而不是模型凭空编造。绝不与用户争论图片里有什么。

## 用户偏好：精简 + 无验证

该用户已明确要求：

### 精简（Be Concise）

- 去掉所有废话、多余的解释和冗长的开场白
- 不要 "我来帮你分析" / "Let me explain" 这类开场白 —— 直接给答案
- 用最少的字传达完整含义
- 优先用表格或项目符号，而不是大段文字
- 当用户说 "精简一些" 时，删掉 30-50% 的文字：去掉形容词、填充语和冗余的重复表述

### 无验证（No Verification Section）

- **不要**包含 "验证"（Verification / Validation）小节或章节
- 应省略的内容举例："验证方法"、"如何验证"、"改之前 dump 一下..."、
  前后行为对比表、要运行的测试命令，以及任何
  "可以这样验证" 之类的说明
- 输出应该只有解决方案/预测/结论 —— 而不是一份
  如何确认其有效性的指南
- 如果自然响应中带有验证步骤，要么整个删掉，要么
  把要点（最多一句话）合并进正文流程

### 图片提取（Image Extraction）— 关键

- 当用户用 `!mk` 发送图片（且没有其他提示词）时，输出只能是图片里的原始
  文本。**其他什么都不要。**
- 不要添加：表格、分析、解释、评论、标题、标签、
  "图片内容："，或任何解读性内容
- 只输出提取到的文本行，逐字照抄。如果图片显示 7 行，
  就输出 7 行 —— 不多不少。
- 如果用户说 "你少了一行"，**用户是对的** —— 立即重新提取，
  不要争辩或坚持说提取完整了。视觉模型并非万无一失；
  用户了解自己的内容。
- 对于顶部行可能被截掉的截图（例如滚动位置导致），
  用户可能会与之前的图片对比 —— 如果已知的一行缺失，应把它
  标注为很可能是截图问题，而不是声称图片里没有它。
- 视觉模型尺寸限制：Qwen VL 模型要求宽度 > 28px 且高度 > 28px。
  任一维度 ≤ 28px 时，API 会返回 HTTP 400。请用户用更大的
  截图区域重新截图。

### 格式：单一代码块

- 整个响应必须在单个外层代码围栏 ```` ``` ```` 内
- 不要嵌套代码围栏（内部代码示例用 4 空格缩进）
- 外层代码围栏前后不要有任何文字
- 外层围栏里是纯 Markdown —— 用户会把它复制进 Typora
- 核对最终输出：如果平台显示了多个代码块或块外文字，就调整
